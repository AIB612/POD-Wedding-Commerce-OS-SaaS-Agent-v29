  本文档是 POD.AI 站内客服 Agent 的“标准”：它是什么、能做什么、不能做什么、
  怎么用、用什么数据、按什么标准清洗、用什么指标衡量、在哪里验证、
  每个文件是干什么的。每条标准都有编号，方便引用和检查。

  它由独立版“POD 独立 Agent 标准文档 1.0”改写而来。独立版是一个可单独部署的
  Agent（适配器 + n8n + Supabase）；本版是已经集成进 POD.AI 网站的实际实现，
  所有条款以 21ca881 的代码为准，代码里没有的功能不写进来。
  与独立版的逐项差异见附录 B。

  设计原则：
    · 集成：Agent 跑在网站自己的 Node.js 进程里，直接调用网站的商品目录、
      报价、订单、物流、优惠码服务，不另建数据源，不经 n8n / Supabase。
    · 本地优先：自有规则引擎 + 店铺数据先答；置信度 ≥ 0.6 一律本地回答。
    · 云模型可选：只有复杂或匹配不上的问题，且服务器配置了模型密钥时才调用
      LLM；当前生产环境未配置密钥，全部走规则引擎（mode = rules）。
    · 数字只来自我们的工具：价格、运费、日期、订单数据永远由服务器计算，
      模型（如启用）只能调用工具，不能自己编。
    · 不打扰：首页没有悬浮聊天气泡；对话在首页主图区内展开。

  修订规则：系统每次更新（代码、配置、后台功能、部署方式），必须同步更新
  本文档对应条款，并在最后的“修订记录”登记提交号、日期和改动条款。

1. 这是什么
======================================================================

1.1 定义
    POD.AI 网站（wed.swisspro.site）内置的客户服务 Agent。访客在首页点击
    POD.AI 标志旁的“Ask POD.AI / AI 助手”，首页主图区变成对话面板。
    它用客户的语言（英 / 中 / 德；法、意见 1.2）回答问题、推荐商品、报价
    （商品价 + 运费 + 预计送达）、查询订单和物流、校验优惠码，并在需要时
    把对话转入后台的人工队列。

    它不是独立系统：商品、价格、运费、订单、物流、优惠码全部来自网站现有
    服务；它不创建订单、不发邮件、不收款。下单仍在设计工作室（Studio）和
    结账页完成。

1.2 核心特性
    · 本地优先：确定性分类器（nlu.js）+ 路由器（router.js）+ 规则回答
      （agent.js ruleAnswer）+ 店铺工具（tools.js）。置信度 ≥ 0.6 本地答。
    · 云模型可选：LLM_PROVIDER + 对应密钥（OPENAI_* / XAI_* / DEEPSEEK_*
      支持工具调用；ANTHROPIC_* / GEMINI_* 只用于回答开放问题）。
      未配置时自动只用规则引擎，并在答复后提供“转人工”。
    · 报价 = 结账价：运费报价与购物车、结账同一个函数（quoteStorefront）。
    · 订单安全：订单号 + 下单邮箱同时匹配才显示，任何不匹配都返回同一句话，
      每个订单号 15 分钟内最多失败 5 次。
    · 语言：中/英/德 回复模板齐全；法语、意大利语可被识别，护栏/转人工/
      错误提示有法、意版本，其余回复模板回落到英文（见 2.1 F10）。
    · 后台：Admin “AI 客服 / Chat agent”，管理员登录后可用。
    · 嵌入：任何网站加一行 <script src="https://wed.swisspro.site/pod-agent/
      widget.js" async> 即出现 POD.AI 对话按钮（同一 /api/pod-agent/chat）。

1.3 边界（不做什么）—— 由代码强制，不依赖 AI 自觉
    1.3.1 不决定退款、补发、取消已付款订单：提到退款即转人工
          （guardrails.js REFUND_RE）；退换货只给政策说明。
    1.3.2 不自行发折扣：销售折扣默认关闭；开启后也只能“申请”，由规则决定
          （每位客户周期内一次、每月上限、需邮箱、一次性码）。
    1.3.3 不承诺具体送达日期：只给“预计 x–y 日”，并说明付款并确认效果图后
          才开始生产。
    1.3.4 订单号 + 下单邮箱一致才透露订单信息；不存在与邮箱错误同一答复。
    1.3.5 不收集银行卡号 / IBAN / CVV / 密码：含此类内容的消息被拒绝且不保存
          原文；卡号在存储前被脱敏；付款只在结账页（TWINT / PayPal / 卡）。
    1.3.6 不向客户透露成本、利润、密钥名称：/api/pod-agent/status 只返回
          strategy、mode 和代码常量（阈值、KPI 数、工具数、语言），不返回
          缺少的密钥名，也不返回任何业务统计。
    1.3.7 知识库没有答案时不编造：规则模式回复“不确定 + 能帮什么 + 转人工”；
          LLM 模式被要求只用检索到的知识，不够就说向团队确认。
    1.3.8 无 LLM 时不假装：直接给最佳规则答案，并附“回复‘转人工’即可”。
    1.3.9 不修改业务数据：聊天端不暴露下单、开票、退货判定等写入工具
          （唯一可写的是：转人工队列记录；以及开启后才有的一次性折扣码）。
    1.3.10 不自动发邮件：转人工只进后台队列，团队从自己的邮箱回复客户。
    1.3.11 不接受改写规则的指令：提示词注入被拒绝，且不会转给模型。

1.4 与独立版的关系（摘要，详见附录 B）
    保留：对话主流程、护栏和转人工规则、工具循环、提示词规则、销售折扣规则、
          指标、数据检查（K/C 项）、👍/👎 评价。
    替换：数据源（Shopify/本地 JSON 适配器 → 网站自有服务）、存储（Supabase →
          data/store.json）、运费（Excel 价格表 → quoteStorefront）、物流查询
          （51Tracking → 自有承运商发货记录）、知识库（faq.md → knowledge.js +
          后台自定义问答）、网页组件（右下角气泡 → 首页主图区面板）、
          后台登录（独立账号 → 网站管理员登录）。
    跳过：n8n、WhatsApp/Instagram/邮件渠道、定时任务（延误致歉、提醒、
          每周指标邮件）、选项图片卡片 + 邮件账单下单流程、运费校准、
          AGENT_MODE 三模式开关、owner/editor/viewer 角色、eval.json 评测集。

3. 如何使用 Agent
======================================================================

3.1 客户怎么用（无需培训）
    3.1.1 网页：首页页头 POD.AI 标志右侧点“Ask POD.AI”（中文界面“AI 助手”，
          德文“POD.AI fragen”）。首页主图区变为对话面板；再点一次、点
          “Back to the scene”或按 Esc 恢复主图。没有右下角悬浮气泡。
    3.1.2 直接打开：任何页面链接到 /?ask=1 或 /#ask 即自动打开对话；
          加 &q=文字（最多 200 字）会预填输入框，但不会自动发送
          （/agent.html“联系团队”用 /?ask=1&q=Talk to a person）。
    3.1.3 面板：标题、新对话按钮、消息区（内部滚动）、快捷问题（chips）、
          输入框（最多 1000 字）、“不要在对话中发送卡号或密码”提示。
          面板高度 = 视口高度 − 吸顶页头高度，输入框始终可见；
          ≤ 1000px 宽、≤ 760px / ≤ 620px 高、≤ 720px 宽（手机）各有压缩布局。
    3.1.4 每条 AI 回复下可点 👍 / 👎；回复中的 /studio.html、/account、
          /shipping、/returns 等站内路径和 https 链接可点击。
    3.1.5 会话保存在当前浏览器标签页（sessionStorage，最多 40 条）；
          “新对话”重新开始。没有跨渠道合并。
    3.1.6 其他网站：嵌入 widget.js（见 7【server/pod-agent】widget.js）。
          右下角（data-position="bottom-left" 可改左下）出现对话按钮；
          data-lang en/zh/de，data-country 市场提示，data-api 接口源。
    3.1.7 HTTP：POST /api/pod-agent/chat（见 10.4）；CORS 开放，可从任何
          系统调用，限流同 10.4。

3.2 团队日常操作（SOP）
    3.2.1 每天（5 分钟）
          a. Admin → AI 客服 / Chat agent → Handoffs，看 open 项
          b. 点 Take；用自己的邮箱回复客户（系统不发邮件）
          c. 处理完点 Resolve，AI 恢复接待该会话
          d. 没有自动提醒；超过“人工回复时间”的未解决项会在 Data check
             显示为 C3 错误
    3.2.2 每周一（30 分钟）
          a. Overview：看 15 项 KPI 的 PASS / WARN，本地回答 % 与 LLM %
          b. 把“Unanswered questions”逐条写进 Knowledge
          c. Conversations：打开带 👎 的会话，修正知识或商品资料
          d. Data check：把 error 清零，分数 ≥ 85
    3.2.3 每月（1 小时）
          a. 核对 Price list、Fees & tax（区域、免运费门槛、承运商时效）
          b. 核对 Carriers 区 YunExpress / 4PX 费用规则与真实账单
          c. 看 Handoff reasons，调整知识库或网站说明
          d. 季节 / 节日信息写进 Knowledge

3.3 转人工处理标准
    3.3.1 触发（guardrails.js handoffCheck，按顺序）：
          要求人工（含“转人工/人工/客服/真人”等）、辱骂、法律/拒付/报警威胁、
          极度愤怒（如“!!!”“气死”）、退款、连续未解决 ≥ 阈值（默认 3）、
          单会话 token 超过上限（默认 40000，仅 LLM 模式会累计）。
          LLM 模式下模型分类器判定的 wants_human / abusive / threat /
          angry 同样触发。
    3.3.2 结果：会话状态 handed_off，生成 agent_handoffs 记录（原因、摘要、
          邮箱、订单号、最近 12 条消息）；客户收到“已转交团队，X 小时内回复”，
          没有邮箱时请客户留下邮箱。之后客户的消息只追加进该记录，AI 不再回答。
    3.3.3 时限：按后台“Team reply time”（默认 24 小时，1–168）。
    3.3.4 处理完毕必须 Resolve，否则该会话一直静音。
    3.3.5 处理中产生的新知识，当周写进 Knowledge。

4. 如何准备数据：哪些数据、清洗标准、数据格式
======================================================================

4.1 “训练”的含义
    不对模型做微调。“训练”= 持续改进 Agent 使用的数据和规则：
      · 知识（内置问答、自定义问答、商品资料）→ 决定能答对什么
      · 店铺设置（价格、运费、时效、税、付款方式）→ 决定报价和事实
      · 规则（同义词、意图、转人工、折扣）→ 决定能做什么（改规则要改代码）
      · 自动化测试 → 衡量是否变好
      · 未答问题、👎、转人工原因 → 告诉你下一步补什么
    原则：AI 不会自己学习；每周补数据，每周看指标。

4.2 数据清单

4.3 数据清洗标准
    4.3.1 通用
      Q1  准确：与网站、政策、结账页一致
      Q2  具体：写数字、单位、条件
      Q3  绝对日期：写 "10 December 2026"，不写“下周”
      Q4  无占位符：不能有 TODO、TBD、xxx、[ ]、待定、???（Data check K5）
      Q5  无内部信息：不能有成本价、利润、毛利、供应商价格（K6）
      Q6  无个人数据：不能有客户姓名、地址、订单号
      Q7  无测试链接：不能有 localhost、example.com
      Q8  时效、税、付款、包邮等店铺事实不写死在问答里：它们由 knowledge.js
          从实时设置生成，改设置即可
    4.3.2 自定义问答（Admin → Knowledge）
      F1  一条只回答一个问题；答案 ≤ 1200 字符（K4，系统上限 1500）
      F2  标题是客户的问法，以 ? 或 ？ 结尾（K2）；长度 5–200
      F3  答案至少 30 字符（K3），包含完整条件和例外
      F4  不重复（K1）
      F5  关键词（Keywords）写客户会用的词，含中英德同义词，逗号分隔；
          中文按两字词组匹配
      F6  选择语言（en/zh/de/fr/it）；同一问题需要多语言就各建一条
          （系统不自动翻译；未命中当前语言时回落英文）
    4.3.3 商品数据
      S1  每个商品有 en（最好也有 zh、de）名称
      S2  材质名称有多语言
      S3  每个商品在 CH 市场有价格，否则阶梯价为空、推荐时被跳过
      S4  新商品如有常见别名（如“喜帖”“Platzkarte”），加进 nlu.js SYN
    4.3.4 测试用例（server/pod-agent-test.js）
      E1  每加一类意图或修一个误判，就加一条断言
      E2  覆盖报价=结账、中文、订单查询防枚举、推荐预算、护栏、转人工、
          本地路由、后台 KPI、模型工具循环（模拟）
      E3  优先用客户的真实原话（去除个人信息）

4.4 数据格式规范
    4.4.1 自定义问答（agent_settings.custom_faq 中的一条）
          {
            "id": "kb_1a2b3c4d",
            "question": "Can I order a printed sample?",
            "answer": "Yes. Every product can be ordered from 1 piece ...",
            "tags": "sample, test print, 样品",
            "lang": "en",
            "active": true
          }
          · 检索打分：关键词命中 2 分，问题文本命中 1 分，自定义条目 +1；
            规则模式下得分 ≥ 2 才直接作答
          · 自定义条目排在内置答案之前

    4.4.2 聊天请求 / 响应（POST /api/pod-agent/chat）
          请求：{ "message": "Shipping to Switzerland for 10 invitations?",
                  "conversation_id": "c_…", "lang": "en", "country": "CH",
                  "page": "/" }
          响应：{ "answer": "...", "reply": "...", "conversation_id": "c_…",
                  "language": "en", "intent": "shipping_quote",
                  "ui": [ {"type":"quote", ...}, {"type":"chips", ...} ],
                  "mode": "rules", "answered_by": "local",
                  "route": { "path": "local", "confidence": 0.9,
                             "reason": "shop_data", "complexity": [] },
                  "handoff": null, "tools_used": ["quote_shipping"],
                  "message_index": 1 }
          ui 卡片类型：products、quote、order、tracking、chips

    4.4.3 会话记录（agent_conversations）
          id、tenant_id、channel "webchat"、status open/handed_off、language、
          messages（最多 40 条；助手消息带 intent、answered_by、route、
          confidence、tools、unanswered、feedback）、intents、tools、
          paths {local, llm}、slots（product、quantity、country、email、
          order_number、pending）、failed_count、total_tokens、handoff_id、page

    4.4.4 转人工记录（agent_handoffs）
          id "ho_…"、conversation_id、status open/in_progress/resolved、reason、
          summary、customer_email、order_number、language、messages（≤ 30）、
          team_note、created_at、resolved_at

    4.4.5 销售折扣记录（agent_discounts）
          code "HELLO-XXXXXX"、email_hash（SHA-256 前 24 位，不存明文邮箱）、
          conversation_id、percent、created_at、expires_at

5. 用什么指标衡量成功率和输出
======================================================================

5.1 核心指标（Admin → Overview，近 30 天，共 15 项）
    ┌─────┬──────────────────────────────┬──────────────────────────┬────────┐
    │ 编号│ 指标（后台标签）             │ 计算方式                 │ 目标   │
    ├─────┼──────────────────────────────┼──────────────────────────┼────────┤
    │ M1  │ Conversations                │ 会话数                   │ —      │
    │ M2  │ Answered locally             │ 本地回答 / 全部回答      │ 越高越好│
    │ M3  │ Answered by LLM              │ LLM 回答 / 全部回答      │ 参考   │
    │ M4  │ Customer messages            │ 客户消息数               │ —      │
    │ M5  │ Messages per conversation    │ 客户消息 / 会话          │ —      │
    │ M6  │ Solved without a human       │ 未转人工会话 / 会话      │ ≥ 80 % │
    │ M7  │ Handed to the team           │ 转人工会话 / 会话        │ ≤ 20 % │
    │ M8  │ Unanswered replies           │ 未答回复 / 全部回复      │ ≤ 10 % │
    │ M9  │ Positive feedback（CSAT）    │ 👍 / (👍 + 👎)           │ ≥ 85 % │
    │ M10 │ Shipping quotes given        │ quote_shipping 调用次数  │ —      │
    │ M11 │ Product recommendations      │ recommend_products 次数  │ —      │
    │ M12 │ Order lookups                │ find_order + get_tracking│ —      │
    │ M13 │ Open handoffs                │ 未解决转人工（全部时间） │ 越少越好│
    │ M14 │ Guardrail refusals           │ 注入 + 支付信息拒绝次数  │ —      │
    │ M15 │ Chat discount codes          │ 聊天发出的一次性码       │ —      │
    └─────┴──────────────────────────────┴──────────────────────────┴────────┘
    状态：有目标的指标显示 PASS / WARN；无目标的显示 INFO；无数据 NO DATA。
    另有：数据质量分（Data check，满分 100，目标 ≥ 85 且 0 error）。
    注：KPI 列表在 admin.js KPI_IDS（15 项）。公开页 /agent.html 的数字
    （15 项 KPI、10 个工具、阈值 0.6、识别 5 种 / 回复 3 种语言）运行时从
    /api/pod-agent/status 读取，HTML 里的备用值由 test:pod-agent 校验与代码
    一致（440778f 及之前页面误写“13 项”，21ca881 已修正）。

5.2 回答路径表（Overview → Answer routing）
    按“路径 · 原因”统计回复数，例如：
      local · shop_data / local · faq_intent / local · knowledge_match /
      local · follow_up / local · guardrail / local · handoff / local · with_team /
      local · complex:open_ended (no_llm_key) / llm · unmatched /
      local · … (llm_error)
    用途：看多少问题“本该交给 LLM 但没有密钥”，决定是否配置模型或补知识。

5.3 抽查标准（人工流程，每周抽 10 条，系统不自动打分）
    每条回复按以下 8 项打分（1–5 分）：
      1. 事实准确（价格、运费、时效、政策与结账页一致）
      2. 语言正确（客户的语言）
      3. 语气合适（您 / Sie）
      4. 没有编造
      5. 没有泄露内部信息
      6. 转人工时机正确
      7. 卡片 / 报价格式正确
      8. 客户问题被解决或明确下一步（链接到 Studio / 查询订单）

5.4 每周指标邮件
    不提供（独立版的每周 KPI 邮件已跳过）。每周在 Overview 手动查看。

9. 对话流程与角色（本地优先路径 + 云增强路径）
======================================================================

9.1 两个路径
    ┌──────────┬──────────────────────────────┬──────────────────────────────┐
    │          │ 本地路径（默认）             │ LLM 路径（仅配置密钥时）     │
    ├──────────┼──────────────────────────────┼──────────────────────────────┤
    │ 何时走   │ 置信度 ≥ 0.6；或无密钥       │ 置信度 < 0.6（复杂/未匹配）；│
    │          │                              │ 或本地规则未找到答案         │
    │ 分类     │ nlu.js 规则分类              │ 规则分类 + 模型 JSON 分类器  │
    │          │                              │ （补充情绪/人工/威胁等）     │
    │ 回答     │ 模板 + 工具结果 + 知识原文   │ 模型 + 工具循环（≤ 4 次）或  │
    │          │                              │ 基于知识的直接回答           │
    │ 数字     │ 工具计算                     │ 仍只能来自工具               │
    │ 失败时   │ “不确定 + 转人工”chips       │ 回落本地答案（llm_error）    │
    │ 成本     │ 0                            │ 按 token 计费                │
    └──────────┴──────────────────────────────┴──────────────────────────────┘

9.2 角色
    对外（客户）：
      R1 访客          匿名，可咨询、看商品、要报价、校验优惠码
      R2 已验证客户    给出“订单号 + 下单邮箱”→ 可看订单状态、预计送达、物流
                       （运单号本身也可查询物流状态）
      R3 转人工中      AI 静音，消息追加到转人工记录，Resolve 后恢复
    对内（团队）：
      管理员           网站 admin 登录后可用全部 Chat agent 功能；修改设置需
                       写操作确认。没有 owner / editor / viewer 分级。

9.3 对外流程 A：咨询与报价（最常见）
    ① 打开        首页点“Ask POD.AI” → 面板显示欢迎语 + 4 个快捷问题（前端
                  i18n 文案，不调用接口）；客户发“你好”时服务器回复后台设置
                  的欢迎语（空则默认）
    ② 提问        “Shipping to Switzerland for 10 invitations”
                  分类：shipping_quote；商品 invitation、数量 10、国家 CH
    ③ 补槽        缺商品 → 问商品（chips：邀请卡/菜单卡/席位卡/迎宾牌）；
                  缺国家 → 问国家（chips：瑞士/德国/奥地利/法国）；
                  下一条只给“Germany”也会接着报价（follow_up）
    ④ 报价        quote_shipping → 【报价卡片】：数量 × 单价 = 小计；
                  标准 / 快递运费（或免费）与预计送达；含/不含增值税说明
    ⑤ 推荐        “Recommend wedding favours under CHF 10”→【商品卡片】
    ⑥ 下单        客户点卡片或链接进入 Studio 定制 → 购物车 → 结账付款
                  （Agent 不创建订单、不开账单、不发邮件）
    保护：价格每次由服务器重新计算；快递/标准与结账同源。

9.4 对外流程 B：查订单和物流
    ① 客户：“Where is my order?”→ 要订单号（如 POD-2026-…）和下单邮箱
    ② 只给订单号 → 先要邮箱，此前不显示任何订单信息
    ③ 两者匹配 → 【订单卡片】：状态（待付款/已付款/待确认效果图/生产中/
       已发货/已签收/已取消）、预计送达、承运商和运单状态
    ④ 不匹配或不存在 → 同一句提示 + /account#find-order；5 次失败锁 15 分钟
    ⑤ 只给运单号 → 在自有承运商发货记录中查 → 【物流卡片】：承运商、
       状态、最新事件、追踪链接
    ⑥ 延误：不主动通知（后台 Carriers 区有无更新 / 未签收天数告警）

9.5 对外流程 C：售后 / 退换货 / 取消
    给出政策原文（个性化商品不支持无理由退货；瑕疵/破损/与效果图不符 14 天内
    凭订单号和照片联系；生产前可免费修改或取消）。提到退款 → 转人工。

9.6 对外流程 D：转人工
    触发见 3.3.1 → 生成队列记录 → 告知“X 小时内回复”，没有邮箱则请客户留邮箱
    → 团队在 Admin 处理并用自己的邮箱回复 → Resolve → AI 恢复。

9.7 本地优先的具体判断（router.js decideRoute，440778f）
    · 店铺数据意图（shipping_quote、price、order_status、tracking、discount、
      recommendation、greeting、thanks）：
        有对应实体 0.9、无实体 0.8，每个复杂度标记 −0.05，最低 0.7 → 本地；
        含开放式问法（why / compare / 帮我写 / 哪个更好 / 建议…）→ 0.55 及以下
        → LLM 路径（模型也必须调用工具取数）
    · 跟进消息（补国家、数量、商品、邮箱、订单号、运单号）：0.8 → 本地
    · 政策 / FAQ 意图（return_request、cancel_or_change、delivery_time、customs、
      vat、payment、proof、website、product_question、contact_info）：
        0.85 / 0.8 − 惩罚（开放式 −0.3，超长 >220 字或 ≥2 个问号各 −0.1）
    · 未分类但知识库得分 ≥ 2：min(0.85, 0.5 + 0.1 × 得分) − 惩罚
    · 其余：0.3 − 0.05 × 复杂度标记数 → unmatched
    · 置信度 ≥ 0.6 → 本地；本地若未找到答案且有密钥 → 交给 LLM
      （原因加 rules_unanswered）
    · < 0.6 且无密钥 → 最佳本地答案 + “如未解答可转人工”+ chips
      （原因加 no_llm_key）
    · 护栏、转人工、静音中的回复一律记为 local（原因 guardrail / handoff /
      with_team）

9.8 每条消息的处理顺序（agent.js handleChat）
    ① 校验（空消息、≤1000 字）、聊天开关  ② 取或建会话  ③ 每会话限流
    ④ 支付信息拒绝（不存原文）→ 卡号脱敏 → 注入拒绝
    ⑤ 已转人工 → 追加到队列，AI 静音  ⑥ 规则分类
    ⑦ 护栏 / 转人工判断  ⑧ 路由：本地 / LLM / 无密钥回落
    ⑨ 保存（answered_by、route、confidence、tools、unanswered）并返回

10. 运行模式与部署

10.1 模式切换
    没有 AGENT_MODE。模式由服务器 .env 自动决定：
      未设 LLM_PROVIDER 或缺对应密钥     → rules（当前生产）
      LLM_PROVIDER=openai|chatgpt + OPENAI_API_KEY + OPENAI_MODEL     → llm_tools
      LLM_PROVIDER=xai|grok + XAI_API_KEY + XAI_MODEL                 → llm_tools
      LLM_PROVIDER=deepseek + DEEPSEEK_API_KEY（DEEPSEEK_MODEL 可选）  → llm_tools
      LLM_PROVIDER=anthropic / gemini + 对应 *_API_KEY、*_MODEL       → llm_answers
    三种情况下策略都是 local_first。改 .env 后需重启应用。
    密钥只放服务器 .env，不进仓库、不进本文档。

10.2 部署环境
    · 服务器：rs8-fra（CloudLinux，Node.js 应用 pod-wedding，目录 ~/pod-wedding）
    · 代码：GitHub 仓库 feature/home-en-images 分支（main 快进到同一提交）
    · 数据持久化：.env STORE_PERSIST_PATH=./data/store.json；会话、转人工、
      设置、自定义问答、折扣记录都在其中（agent_* 集合）。data/ 目录不进 git，
      git pull 不会覆盖；部署前后不要删除 data/。
    · 相关开关：LOGISTICS_ENABLED=true（承运商规则与物流同步）

附录 D  独立 Shopify App「Pod.AI」
----------------------------------------------------------------------
  D.1 是什么：只把客户聊天 Agent 打包成可装到任何 Shopify 店铺的 App。
      与「POD Wedding Studio」是两个不同的 Partner App，凭据分开
      （AGENT_SHOPIFY_API_KEY / AGENT_SHOPIFY_API_SECRET，只放服务器 .env）。
  D.2 组成：
      · 店面聊天：主题应用扩展 app embed（apps/shopify-agent/extensions/podai-chat），
        商家在 主题编辑 → App embeds 打开，不改主题代码、不注入脚本。
      · 聊天接口：/apps/podai/chat → App Proxy → /shopify-agent/proxy/chat，
        服务器校验 Shopify 签名，店铺只从签名里取。
      · 后台：/shopify-agent（App Bridge + session token），概览 KPI、转人工队列、
        知识库、设置、试聊、安装说明。
      · Webhook：/shopify-agent/webhooks —— app/uninstalled 与三个 GDPR 主题，
        HMAC 错误返回 401，其余返回 200。
  D.3 数据隔离：每个店铺一个租户（数据在 podai_* 集合） shopagent_<店铺域名>，只来自已校验的
      session token / App Proxy 签名 / webhook HMAC；店铺之间、与 POD.AI 之间
      不共享会话、转人工、知识库；POD.AI 内置 FAQ、商品、价格不会出现在店铺里。
  D.4 数据来源（全部来自该店铺，Admin GraphQL + 该店的离线令牌；不读 POD.AI 网站任何数据）：
      · 商品目录：products / variants / collections / metafields（read_products）
      · 价格：variant price、店铺币种、taxesIncluded（read_products）
      · 运费：delivery profiles → zones → rates；计算型运费或无区域 → 运费政策 +
        “结账时计算”（read_shipping）
      · 订单与物流：订单号 + 邮箱；fulfillments.trackingInfo → 承运商接口
        （YunExpress sandbox / 4PX production）→ 51Tracking v4（TRACKING51_API_KEY，
        未登记先登记）→ Shopify 查询链接；显示状态、最新节点、时间线；缓存 30 分钟；
        只读，不创建承运商订单（read_orders）
      · 优惠码：只校验客户给出的码是否有效，不列出任何码（read_discounts）
      · 退货 / 付款说明：店铺政策 shopPolicies（read_legal_policies）
      · 商家问答：Pod.AI 后台 → Knowledge（优先于自动答案）
  D.4b 边界：Pod.AI 使用自己的引擎副本（server/shopify-agent/engine，由站内 Agent 复制）
      和自己的数据集合（podai_*）；不修改、不调用站内 Agent（server/pod-agent）及其
      后台、网站服务。仅共用：存储 saas-store.js、加密 utils/crypto.js、承运商查询客户端
      logistics/{yunexpress,fourpx,http}.js（只调用查询）；站点唯一挂载点是 create-app.js
      的一行。test/audit.test.js 检查边界。
  D.5 验证：node server/shopify-agent/test/app.test.js、tracking.test.js、audit.test.js
      （签名、安装、店面聊天、店铺数据、隔离、后台、webhook、物流、边界；
      POD.AI 结账 CHF 6.34 / 13.15 不变）。
  D.6 需要 Partner 账号的步骤与上架清单：见 apps/shopify-agent/README.md。
